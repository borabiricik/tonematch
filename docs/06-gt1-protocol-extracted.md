## 1. SysEx framing

### 1.1 DT1 (set) / RQ1 (request)
`SE:1687-1705` `createSysExAddress(type, addr, payload)`:
```
"F0," + maker_id + "," + hex2(deviceID) + "," + model_id + "," + (type==0 ? "11" : "12") + "," + addr + "," + payload + "," + checksum + ",F7"
```
- `maker_id` = `41` (addressmap `id.maker_id`).
- `model_id` = **`00 00 00 30`** (4 bytes). BTS always uses `model_id_gt001` for the GT-1: `SE:262`
  (`this.addressMap.model_id = this.addressMap.addressObj.id.model_id_gt001`). The JSON has `"model_id_gt001": "00,00,00,30"`.
- Command byte: RQ1 = `11`, DT1 = `12` (`AM:14-16`).
- Address = 4 bytes. RQ1 payload = 4-byte size. DT1 payload = N data bytes.

```
DT1: F0 41 dd 00 00 00 30 12 a1 a2 a3 a4 d1 … dn cs F7
RQ1: F0 41 dd 00 00 00 30 11 a1 a2 a3 a4 s1 s2 s3 s4 cs F7
```
When BTS is not connected it replaces the header with `41,00,00,00,00,06`. That is a placeholder for offline simulation
and is never sent (`SE:1691-1694`, `SE:675-686`).

### 1.2 Checksum
`SE:1707-1726`: sum every byte of address + payload (data for DT1, size for RQ1), then `cs = 128 - (sum % 128)`, with 128
mapped to 0. This is the standard Roland formula `(128 - sum % 128) % 128`.

### 1.3 Device ID — how BTS finds it
1. `getDeviceID()` sends `request_device_id` = **`F0 7E 7F 06 01 F7`** (Identity Request to all devices) (`SE:2268-2272`, JSON).
2. It takes the device ID from **byte [2] of the Identity Reply**: `params.deviceID = convertDecimal(paramArray[2])` (`SE:915-923`).
3. `getID()` then sends **`F0 7E 00 06 01 F7`** (hard-coded, `SE:2274-2279`). It accepts the device only if the reply hex
   string starts with **`F07E000602413003000000000000F7`** (`SysExParams.as:checkID`). The native layer formats bytes as
   `%02X` (string in `RWCANE.dll`), so the `00` really is one byte with value 0x00.

So the reply BTS expects is `F0 7E 00 06 02 41 30 03 00 00 00 00 00 00 F7` (family 0x0330, number 0x0000, version 0,0,0,0).
**By BTS's own logic the GT-1 device ID is 0x00.** That gives DT1 header `F0 41 00 00 00 00 30 12`.
This contradicts the `0x10` assumption in `06-gt1-protocol.md`. `[VERIFY ON DEVICE]` The identity request is harmless, so
the tool should send `F0 7E 7F 06 01 F7` and use reply byte [2] instead of hard-coding the ID.

Inbound validation (`SE:1728-1773`): `[0]=F0, [1]=41, [2]=deviceID, [3..6]=00 00 00 30, [7]=12, last=F7`.
Address = bytes `[8..11]` (`SE:1801-1805`). Data = bytes `[12 .. len-2)` (`SE:2570-2575`).
BTS **does not verify the checksum** of incoming messages.

BTS bug to avoid copying: `request()` (`SE:699-708`, used only by `requestDataFunc`) builds the header with
`zeroPadding(deviceID)`. `deviceID` is stored as a decimal string, so the value is not converted back to hex. It only
matters for IDs above 9. Every other path converts the ID correctly.

### 1.4 Message sizes and splitting
- **Writes are never one bulk DT1.** A whole patch goes out as **24 DT1 messages** of 33–65 data bytes each. The largest is
  65 bytes at `60,00,02,00`. The longest message is 79 bytes. The block table is `temporaryDecimalPatchSize` (`SE:353-425`):

| # | addr (a3,a4) | bytes | # | addr | bytes | # | addr | bytes |
|---|---|---|---|---|---|---|---|---|
| 1 | 00,00 | 64 | 9 | 04,00 | 64 | 17 | 08,00 | 64 |
| 2 | 00,50 | 48 | 10 | 04,41 | 63 | 18 | 08,50 | 48 |
| 3 | 01,00 | 64 | 11 | 05,01 | 63 | 19 | 09,10 | 48 |
| 4 | 01,40 | 64 | 12 | 05,40 | 64 | 20 | 09,50 | 48 |
| 5 | 02,00 | 65 | 13 | 06,00 | 64 | 21 | 0A,10 | 33 |
| 6 | 02,41 | 63 | 14 | 06,40 | 64 | 22 | 10,10 | 64 |
| 7 | 03,00 | 64 | 15 | 07,00 | 64 | 23 | 10,50 | 48 |
| 8 | 03,40 | 64 | 16 | 07,40 | 64 | 24 | 11,00 | 64 |

  The blocks total 1423 bytes, with no overlaps. They cover **all 995 TemporaryParams fields**. 428 of the written bytes
  have no field, and BTS sends `00` for them because `getParamForEx` defaults to 0. `gaps.py` checks this. Skipped ranges
  such as `00,40-4F`, `08,40-4F`, `09,00-0F`, `0A,31-0F,7F` and `10,00-0F` are never written.
  The address step inside a block wraps at 7 bits: after low byte `7F` comes `(page+1),00` (`TP:6581-6608`).
- **Reads use large RQ1s.** The device answers with several DT1 packets:
  - Temporary area and user/preset patch: 3 × RQ1 with size `00,00,08,00`, at `xx,yy,00,00`, `xx,yy,08,00` and
    `xx,yy,10,00` (`getTemporaryPatchSize` `SE:426-435`; size string built at `SE:2328-2334` / `SE:2336-2348`).
    The reply is a stream of DT1s. BTS sends the next RQ1 when the packet whose address low bytes are `07,44` or `0F,44`
    arrives. The read is complete when the packet at `10,10` arrives (`SE:1083-1094`, `SE:1109-1133`, `SE:1467-1478`).
  - System: 24 × RQ1 of 14–80 bytes (`systemDecimalPatchSize` `SE:280-352`).
  - Patch names: RQ1 at `10,ii,00,00` (user) or `20,ii,00,00` (preset), size `00,00,00,10` = 16 bytes (`SE:2404-2453`).

### 1.5 Timing, timeouts, retries
| What | Value | Evidence |
|---|---|---|
| Gap between patch-write DT1 blocks (temp or user slot) | **30 ms** (`Timer(30)`) | `SE:98`, `SE:1587-1656` |
| Gap after each patch-name reply before the next RQ1 | 30 ms | `SE:1311`, `SE:1344` |
| Write-dialog steps (name → category → category2 → patch_write) | 30 ms each | `SelectWritePatchNoPopup.as:187-219` |
| Request timeout | 3000 ms, up to 5 retries (`retryCount < 6`), then error dialog | `SE:154`, `SE:2350-2363`, `SE:2426-2439` |
| Patch-change resend until the device echoes `current_patch_no` | 500 ms | `SE:172`, `SE:2534-2550` |
| After `editor_comunication_mode=01`, before the first bulk read | 100 ms | `TCL:612-619` |
| After `editor_comunication_mode=00` on port change, before reconnecting | 1000 ms | `TCL:462-468` |
| Wait after the device's `patch_write` reply before reloading names | 1000 ms | `SE:2629-2635` |
| Connect timeout (identity) | 5000 ms | `TCL:175` |
| Patch-map sort reply timeout | 1000 ms | `SE:178`, `SE:1676-1685` |

BTS does not wait for any ACK after a DT1 write. It relies only on the 30 ms pacing.

## 2. Connection handshake

Command addresses (addressmap `command`):

| name | address | size |
|---|---|---|
| editor_comunication_level | 7F,00,00,00 | 1 |
| editor_comunication_mode | 7F,00,00,01 | 1 |
| running_mode | 7F,00,00,02 | 1 |
| patch_copy | 7F,00,01,00 | 4 |
| patch_write | 7F,00,01,04 | 2 |
| tuner_multi_mode_str_1..6_pitch | 7F,00,02,00..0A | 2 |
| tuner_single_mode_pitch | 7F,00,05,00 | 2 |
| usb_direct_mon | 7F,00,06,00 | 1 |
| usb_in_out_mode | 7F,00,06,01 | 1 |
| quick_setting_wirte | 7F,01,00,00 | 2 |
| ab_utilty | 7F,01,00,02 | 1 |
| patch_clear | 7F,01,00,03 | 1 |
| patch_initialize | 7F,01,00,04 | 1 |
| manual_sw | 7F,01,00,07 | 1 |
| patch_map | 7F,70,00,00 | 1 (BTS requests 0x7F) |
| update_patch_map | 7F,71,00,00 | 1 |

Connect sequence (`TCL:567-714`):
1. `F0 7E 7F 06 01 F7` → read device ID from reply byte [2] (`SE:2268`, `SE:915`).
2. `F0 7E 00 06 01 F7` → identity check (§1.3). On success, `connected=true` and the `RECOGNIZED` event fires (`SE:924-937`).
3. **RQ1 `7F,00,00,00` size 1** (editor_comunication_level) (`SE:2281-2285`). BTS stores the value in
   `params.editorComunicationLevel` (`SE:938-949`) and **never checks it** (grep: no other reads). It is a version probe.
4. **DT1 `7F,00,00,01 = 01`** (editor_comunication_mode ON) (`TCL:612-619` → `SE:2292-2305`). BTS waits 100 ms.
   This mode most likely makes the GT-1 push DT1s for changes made on the unit, such as knob moves and patch changes
   (`current_patch_no`, running_mode, tuner pitch). BTS depends on those pushes (`SE:825-873`, `SE:1190-1278`).
5. Reads all 198 patch names (16 B each, 30 ms apart) (`TCL:621-634`).
6. Reads system in 24 blocks (`TCL:636-670`), the temporary area (3 RQ1), and setup `current_patch_no` (`TCL:682-694`).
7. RQ1 `running_mode` and RQ1 `manual_sw` (`TCL:711-712`).

`running_mode` values (from `Tuner.as:240-262, 795-803, 1128`): **0 = play/normal, 1 = tuner (single), 2 = tuner (multi)**.
BTS writes 01/02 when it opens the tuner and **00 when it closes it**. Keep it at 0 while writing patches.

Disconnect / exit (`TCL:940-952`): **DT1 `7F,00,06,00 = 01`** (usb_direct_mon ON), then **DT1 `7F,00,00,01 = 00`**
(editor mode OFF). BTS also sends mode OFF before switching ports (`TCL:462-468`).

**Needed before temp-patch writes:** in BTS the only state is editor mode = 01 and a successful identity/connect. No
unlock or level check exists in code. Recommended for our tool: identity → (optional) RQ1 level → mode=01 → wait 100 ms
→ writes → mode=00 on exit. `[VERIFY ON DEVICE]` whether writes work without mode=01.

## 3. TSL params dict ↔ temporary-area addresses

### 3.1 What a TSL `params` dict is
`params` is a JSON-serialised `TemporaryParams` object (`PatchData.getModel()` uses `JSON.stringify(this.params)`). It
holds every public var **plus every getter**. Loading goes through `TemporaryParams.restore()` (`TP:2017-2030`): for
each key (except `chainParams`) with `hasOwnProperty`, it sets `obj[key] = value`, then rebuilds `chainParams` from
`fx_chain_position1..20`.

The authoritative key↔address table is in `TP` itself:
- `TP:2516 setData(addrInt, value)` (receive) and `TP:6644 getParamForEx(addrInt)` + `TP:11195 getPatchPreampData`
  (send) contain long `if(param1 == N) this.<field> = …` chains.
- `addrInt = a3*256 + a4` of a `60,00,a3,a4` address (`TP:6588`, `SE:1106`). Bulk replies are unpacked with 7-bit
  wrap (`TP:2489-2514`).
- The UI side confirms the naming: the AddressMap property is **`"temp_" + <tsl key>`**
  (`ParameterListGroupLogic.as:223-230`: `_loc4_ = "temp_" + param1.id; this.addressMap[_loc4_].address`).
  `AM.setAllAddress()` builds those properties from the JSON names. FFDec could not decompile it, so the parsed `TP`
  table is used instead.

### 3.2 Name rule (JSON `name` → key)
Approximately: lowercase; `#`→`_s`; a `:` with no surrounding space is dropped (`PS1:MODE`→`ps1mode`); every other
run of non-alphanumerics becomes `_`; size-2 entries take `_h` (and the next byte takes `_l`). Examples:
`PREAMP A: GAIN`→`preamp_a_gain`, `FX1: HARMONIST: HR1:F#`→`fx1_harmonist_hr1f_s`, `DELAY: DELAY TIME`→`delay_delay_time_h`.
This rule matches 892 of 926 named entries. The 34 exceptions include `PRM_` prefixes being dropped
(`PRM_NS2_THRESHOLD`→`ns2_threshold`), `AC.GUITAR SIM`→`acsim`, `MASTER_CATEGORY2`→`patch_category2`,
`PRM_CTRL_EXP_PEDAL_*`→`ctl_exp_pedal_*`, `DELAY: PAN TAP TIME`→`delay_tap_time`, `ASSIGN6: WAVE RATE 3257`→`assign6_wave_rate`
and `PRM_FX2_OVERTONE_DIRECT_MIX`→`prm_fx2_overtone_direct_level`.
**Don't rely on the rule. Use the parsed table** (`gt1_temp_field_map.json`).

### 3.3 Coverage, from `gt1_tsl_map_check.py` over 99 presets
- Unique TSL keys: **1040**. Keys with an address: **995** (every TemporaryParams field). Unmapped: **45**:
  - **24 + 16 aggregate getters** (read-only views; their setters do nothing, `TP:2232-2295`):
    `assign1..8_target`, `assign1..8_target_min`, `assign1..8_target_max`, `delay_delay_time`, `delay_d1_time`, `delay_d2_time`,
    `reverb_pre_delay`, `reverb_dd_delaytime`, `master_bpm`, `fx1/fx2_pitch_shifter_ps1pre_dly`, `…ps2pre_dly`,
    `fx1/fx2_harmonist_hr1pre_dly`, `…hr2pre_dly`, `fx1/fx2_sub_delay_time`. Each equals `X_h*128 + X_l`
    (`TP:2032-2230`). **Ignore them on write. `_h`/`_l` hold the real data.**
  - `patchname`: a real setter. It writes `patch_name1..16` from ASCII, space-padded (0x20) to 16 (`TP:2432-2465`).
    `PatchData.restore` then sets `name` from the TSL's **top-level `name`** (with `" | "` removed), which re-runs
    `patchname` (`PatchData.as`: `set name` → `setPatchParamName`). So the top-level `name` wins over `patch_name1..16`
    and `params.patchname`. All 99 presets agree anyway.
  - `chainParams` (derived from `fx_chain_position1..20`), `patchCategoryName` (null), `currentPatchNo` and
    `prevCurrentPatchNo` (runtime state). These are not sent.
- Address-map temporary has 965 entries: 926 have name+size, and 39 have only an address. Those 39 are the `_l` bytes of
  size-2 values. One of them is duplicated (`60,00,02,40` appears twice), while `60,00,02,3A`
  (`fx1_pitch_shifter_ps1pre_dly_l`) and `60,00,10,71` (`reverb_dd_delaytime_l`) are missing.
- TemporaryParams fields **not in the JSON map** but sent by BTS: `60,00,01,16/17` (`precustom_b_bass_freq/treble_freq`),
  `60,00,10,7F` and `60,00,11,00..0A` (`fx_feedbacker_name0..11`), `60,00,11,0B..16` (`fx_chorus_name0..11`) and
  `60,00,11,17..19` (`ctrl_exp_pedal_led_status_down/up/ctl1`).
- Every raw value in the presets fits in 7 bits (0..127).

### 3.4 Multi-byte values
- The 40 size-2 entries are 7-bit pairs: **value = hi*128 + lo**, with hi at the entry's address and lo at the next
  address. The UI encodes `[floor(v/128), v%128]` (`ParameterComponent.getDoubleByteValue` `:233-238`;
  `ParameterUtil.getDoubleByteData`). Example: `delay_delay_time_h=3, _l=16` → 400 ms.
- `patch_name1..16` sit at `60,00,00,00..0F`, one ASCII byte each, space padded. BTS's dialog limits names to
  16 chars in the range `"-~"` (`SelectWritePatchNoPopup.as:112-113`). `sendPatchName` writes all 16 bytes in one DT1
  to `temporary[0].address` (`ToneCentralUtil.as:17-32`).

### 3.5 Raw ↔ display conversion
TSL values are **raw device bytes**: the fields are filled directly from SysEx bytes (`TP:setData`). The UI conversion is:
- display = `raw*step + (min if min < 0 else 0)` (`ParameterListGroupLogic.as:231` then `ParameterComponent.as:637-640`).
- raw = `(display - (min if min < 0 else 0)) / step` (`ParameterComponent.as:166-178`).
- Examples: `eq_low_gain` (min -20) raw 20 → 0 dB. `fx1_pitch_shifter_ps1pitch` raw 24 → 0. `patch_level`
  (0..200, step 2) raw 50 → 100. `delay_delay_time` (min 1) raw 400 → 400 ms (no offset). `master_bpm` (min 40)
  raw 120 → 120 BPM (no offset).
- Some params use `STEPPER_AND_DROPDOWN_LIST` (`PD:5019+`), for example rates and pre-delays: raw values above the
  stepper max select note-value options from a dropdown. Treat raw as opaque and stay inside the ranges in `PD`.

### 3.6 Quirks that affect what BTS actually sends
- **PREFERENCE: PREAMP** (system `00,00,00,41`; 0=PATCH, 1..3=SYSTEM1..3, `SSD:1802`). When it is not 0, BTS sends the
  **system preamp** values in place of the patch's for temp bytes 0x50..0x11F (`TP:6802-6820`, `getSystem1..3PreampData`).
  This happens for both temp writes and direct user-slot writes. Our tool should read `00,00,00,41` first and warn or
  refuse if it is not 0.
- BTS bug: the send table has `param1 == 115` instead of 2419 for `assign7_target_min_h` (`TP:9880`). BTS therefore
  always sends **0** at `60,00,09,73`. Our tool should send the real value (taken from the receive table).

## 4. Writing a whole patch, saving it, reading it back

### 4.1 Patch → temporary (edit buffer)
`SE:1587-1629 setTemporaryParams(params)`: the 24 blocks in §1.4 go out **in table order**, one DT1 every 30 ms.
Each payload is `params.getExData(addr, size)`. If the device reports a patch change (a pushed `current_patch_no` < 400)
during the write, BTS sets `writeStop`, aborts, reloads and re-sends (`SE:835-852`, `SE:1610-1627`).
Callers: library click, Tone Central and liveset preview (`SideAreaLogic.as:819,857`, `LiveSetLibraryListLogic.as:1478`).

### 4.2 Save temporary → user slot (the WRITE button)
`SelectWritePatchNoPopup.as:187-219` sends these, 30 ms apart:
1. DT1 `60,00,00,00` ← 16 name bytes (space padded).
2. DT1 `60,00,07,0F` ← `patch_category` (0..18, list at `PD:13`).
3. DT1 `60,00,10,76` ← `patch_category2`.
4. **DT1 `7F,00,01,04` ← `[hi, lo]`** with `getPatchNum(index)` = `[floor(i/128), i%128]` (`AM:5099-5106`).
   For user slots **U01..U99 → i = 0..98 → `00 00`..`00 62`**. The dialog only lists `U` entries (`SelectWritePatchNoPopup.as:56-80`).

Example (dev 0x00, U05):
```
F0 41 00 00 00 00 30 12 7F 00 01 04 00 04 78 F7
```
The device answers with a DT1 at `7F,00,01,04`. BTS handles it as `PATCH_WRITE` (`SE:1206-1209`). After 1 s it re-reads
the 99 user names, then the temporary area, then the patch map (`SE:2629-2648`, `SE:1357-1366`, `SE:1127-1131`).
`patch_copy` (`7F,00,01,00`, 4 bytes = src hi,lo + dst hi,lo, with `7F,7F` = temporary, `SE:721-744`) exists but BTS never calls it.

### 4.3 Write a liveset/TSL patch straight into a user slot (no WRITE command)
`SideAreaLogic.as:904-923 doPaste()` (used by paste and "apply liveset"): the address is
**`"10," + hex2(slotIndex) + ",00,00"`**. `SE:1631-1656 setPatchParams` then sends the **same 24 blocks**, replacing
bytes a1,a2 with `10,ii` (`createSetPatchAddresList` `SE:599-617`), 30 ms apart.
- Patch stride: **one step of the 2nd address byte per patch** (`10,ii,pp,oo`). `getPatchAddress("Unn")` =
  `10,(nn-1),00,00`, and for index ≥ 128 it becomes `11,(nn-1-128)` (`AM:5180-5214`). Presets are `20,..` / `21,..`.
- When the batch is done, if a written slot is the current patch, BTS also re-sends that patch to the temporary area
  (`SideAreaLogic.as:925-962`).
- After a drag-reorder, BTS writes the **patch map**: DT1 `7F,70,00,00` ← 50 IDs × 2 bytes, DT1 `7F,70,00,64` ← 49 IDs × 2 bytes,
  then DT1 `7F,71,00,00 = 00`. The reply data `00` means success, anything else is a fault (`SE:1658-1685`, `SE:1258-1269`,
  `SideAreaLogic.as:489-528`). Not needed for a plain single-slot write.

### 4.4 Read a user patch (backup)
`SE:619-626 getPatchParamsFunc("10,ii,00,00")` sends 3 × RQ1:
```
RQ1 10,ii,00,00 size 00,00,08,00
RQ1 10,ii,08,00 size 00,00,08,00   (sent when the reply packet at 10,ii,07,44 arrives)
RQ1 10,ii,10,00 size 00,00,08,00   (sent when the packet at 10,ii,0F,44 arrives; done at 10,ii,10,10)
```
Replies are unpacked with `TemporaryParams.updateData`, using the same addrInt layout as the temporary area
(`SE:1077-1095`). The timeout is 3 s with up to 5 retries (`SE:2336-2363`). The temporary area is read the same way at
`60,00,00,00 / 08,00 / 10,00` (`SE:2328-2334`). For a backup file, store the unpacked fields as a TSL `params` dict.
Its `name` is ASCII from `patch_name1..16` with trailing spaces trimmed (`TP:2467-2487`).

## 5. Patch numbering / current patch

- Setup `current_patch_no` sits at `00,01,00,00`, size 2. **value = b0*128 + b1** (`SE:835-837`, `SE:962-975`).
- Indices (`PD:5489-5509 createParamNoList`): **0..98 = U01..U99**, **99..197 = P01..P99**. There are no banks in BTS.
  `[VERIFY ON DEVICE]` if the GT-1 display uses a bank-style label.
- Select a patch: DT1 `00,01,00,00 ← [i/128, i%128]`. BTS resends every 500 ms until the device pushes back
  `current_patch_no` (`SE:2534-2550`), then reads the temporary area.
- Value 400 is special. When it arrives, BTS keeps the old number in `prevCurrentPatchNo` and does nothing else
  (`SE:838-852`; only values < 400 count as a patch change). Its meaning is unknown; it may be a non-patch state.
- Address for index i: user `10,i,00,00`, preset `20,(i-99),00,00` (`SE:2404-2421`, `SE:2484-2504`).

| 00,00,00,54 | USB: DIRECT MONITOR | sys_usb_direct_monitor | OFF/ON (`SSD:1812`) |
| 00,00,00,56 | LOOP BACK | sys_usb_loop_back | OFF/ON (`SSD:1811`) |
| 00,00,00,57 | USB: SECONDARY OUTPUT LEVEL | sys_usb_secondary_output_level | unit "%"; no UI |
| 00,00,00,7D | INPUT SELECT | sys_input_select | **GUITAR(0) / MIC(1)** only (`SSD:1834`) |
| 7F,00,06,00 | cmd usb_direct_mon | — | BTS only ever sends `01`, on exit (`TCL:944`) |
| 7F,00,06,01 | cmd usb_in_out_mode | — | **never referenced** apart from the AddressMap var (`AM:4606`); no enum or strings |

`SETTING_USB_PARAMS_LIST` (the BTS USB page) has only MIX LEVEL and EFFECT OUT LEVEL (`SSD:178-194`).
The "secondary" audio port code (`SE:2800-2822`, used by Rec/Play) is GT-001 legacy: `secAudioInKey` is never set for the GT-1.
In the effect chain, element 16 is **"USB"**, is not editable (`ChainParams.as`, `isEditable`), and sits at the **last
chain position** in all 99 presets. It is the tap that feeds USB record. Element 18 "MXDV" and element 1 "S/R" are also not editable.

**Answer: BTS shows no way to route USB audio from the PC into the effect chain (no reamp).** INPUT SELECT offers only
GUITAR/MIC. The USB controls are a playback **MIX** level (PC audio mixed into the output), a record level, direct
monitor and loopback. The only unexplained hook is `usb_in_out_mode` (`7F,00,06,01`), which BTS never uses and whose
values are unknown. A read-only RQ1 of that address is the safe first probe. Writing it without documentation is a risk.
**Keep the physical-reamp plan in `01-hardware-gt1.md`.**

## 7. OUTPUT SELECT

- Patch-level: `60,00,00,10` (`output_select`). System-level: `00,00,00,70` (`sys_output_select`).
- **Both use the same option list** (`SSD:1837`, `SETTING_OUTPUT_PARAMS_LIST` `SSD:196-205`, where `tmpID` maps the system id to
  the patch field). 0 **JC-120**, 1 **SMALL AMP**, 2 **COMBO AMP**, 3 **STACK AMP**, 4 **JC-120 RETURN**, 5 **COMBO RETURN**,
  6 **STACK RETURN**, 7 **LINE/PHONES**. The definition says max 8, but only 8 labels exist (0..7).
- **The patch value has no "SYSTEM" option.** System `PREFERENCE: OUTPUT SELECT` at `00,00,00,40` (PATCH=0 / SYSTEM=1,
  `SSD:1769,1801`) decides which value is used. BTS reads and writes the system value when the preference is 1,
  otherwise the patch byte (`SystemManager.as:191`, `EditManager.as:556-570`, `ChainInOutLogic.as:133-146`,
  `OutputSelectPopup.as:117-131`). Value 7 makes the UI draw "LINE/PHONES" (headphones).
- All 99 presets ship with `output_select = 0` (JC-120).

## 8. Minimal recipe for our tool (the same way BTS does it)
1. Open the GT-1 MIDI in/out ports. Send `F0 7E 7F 06 01 F7` and take dev = reply[2] (expected 0x00). Check that the
   reply starts `F0 7E dev 06 02 41 30 03`.
2. Optional: RQ1 `7F,00,00,00` size 1. Then DT1 `7F,00,00,01=01` and wait 100 ms.
3. Optional safety reads: RQ1 `00,00,00,41` (preamp preference, must be 0 for the patch preamp to be used), `00,00,00,40`
   (output-select preference), `00,01,00,00` (current patch).
4. Build the 24 blocks from a `params` dict using the **receive** table (`gt1_temp_field_map.json`); default 0; `_h`/`_l`
   for 2-byte values; name from TSL `name`, space padded. Send each block to `60,00,a3,a4` with 30 ms between DT1s.
5. Save, either way:
   - (a) Like the WRITE button: send name, `patch_category` and `patch_category2` (30 ms apart), then DT1 `7F,00,01,04 = [00, i]`
     (i = 0..98 for U01..U99), then wait for the device's `7F,00,01,04` DT1 or about 1 s.
   - (b) Like paste/apply: send the same 24 blocks to `10,i,a3,a4`.
   Back up first with 3 × RQ1 at `10,i,00/08/10,00` size `00,00,08,00`.
6. On exit: DT1 `7F,00,06,00=01`, then DT1 `7F,00,00,01=00`.
